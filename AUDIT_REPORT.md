# Codebase audit — 2026-11-10

Follow-up: [2026-11-12 verified fixes and compatible refactors](HARDENING_REPORT.md) adds versioned demand-free new training, sealed caches, isolated run manifests and named scoring stages. This original audit and its artifact inventory remain historical evidence; existing models/caches were preserved.

Repository: `RODIONOLIINYK/enterprise-product-recommendation-system`, branch `main`, starting commit `4cbe764`. The working tree was clean at audit start. Source review and runtime probes preceded implementation changes. This audit does **not** implement the shared 176D/192D/224D architecture, retrain models, or inspect held-out purchases.

## Scope and evidence

Reviewed all 21 Python modules, the 25 existing test modules, configuration, README, architecture guide, evaluation history and roadmap. Read only the saved **training/validation** slate caches and checkpoint metadata/weights; no raw purchase CSV or held-out cache was opened. The initial safe suite passed **258 tests and 70 subtests**, with six tests explicitly deselected because they read the unsplit real purchase CSV. Synthetic events after the split boundary are permitted for boundary tests; they are not held-out observations.

Evidence and final validation results are recorded below and in `audit/`. Line references identify the final source tree. “Inactive” means inactive in the reference cached-candidate configuration, not removable from every supported configuration.

## Parameter utilization and numerical routing

The reproducible probe uses the first 64 cached **training** rows and the locally available ranker weights. Candidate vectors are seeded synthetic L2-normalized vectors; prediction day is synthetic `2025-09-30`. This reproduces the reference training input configuration, **not** the exact original training batch or its loss/quality. No optimizer step is taken. Report every named parameter in `audit/gradients.json`, including element counts, graph participation, missing/zero gradients, zero-gradient element counts and norms. Graph participation here means autograd produces a gradient tensor (which can be all zeros).

The model has **866,313 parameters**. The **201,984 ProductTower parameters (23.32%)** are absent from the graph. Entire tensors totaling **33,056 parameters** have exactly-zero gradients (habit/text weights); another **1,024 numerical tabular columns** and **56 excluded history-repeat bias coefficients** are structurally zero-gradient. Embedding padding rows and unused IDs in one batch also have zero gradients, but they are not globally dead parameters. ProductTower FP32 state occupies **807,936 bytes**, excluding serialization overhead; it has no Adam moments when never used.

| Input | Self-attention / cross-attention Q,K,V | Statistical cross-attention bias | Final scoring MLP |
|---|---|---|---|
| Eight profile numbers | No direct memory input | Profile key statistics | Indirectly through attention-weighted context |
| Nine history numbers | No direct memory input | History key statistics; age replaced by `age_days/(age_days+90)`; index 7 excluded | Indirectly through context |
| Thirteen candidate numbers | Not in candidate query | Candidate features plus intercept | Directly concatenated |

Nonzero Q/K/V and bias gradients are observed; padded attention is exactly zero. Eval mode **with autograd enabled** reproduces the inactive pathways; normal `eval()` plus `no_grad()` produces no gradients, as expected. Statistical bias coefficients initialize at zero, so raw statistic-input gradients can initially be zero even though the bias weights learn.

## Temporal analysis and computational alternatives

Demand features are built once at the train cutoff, fed to ProductTower on every training batch, reused as history vectors, cached for retrieval, and reconstructed by standard/discovery loaders. Earlier training transitions therefore receive later-training volume, velocity, buyer, share and recency information. Optional median-SKU quantity has the same issue. This violates strict per-prediction point-in-time semantics even though the validation/test split boundary is respected. The fixed snapshot remains fixed during validation: that is a training-frozen catalogue policy, not a rolling demand implementation.

Customer profiles, sequence events, familiarity first-purchase flags, repeat/unseen target labels and candidate counts are filtered strictly before prediction dates. Customer maxima, quantity/gap references and popularity normalization are fitted on training data; these are conventional train-fitted transforms, distinct from future raw demand values. They still mean appending later training observations can change earlier normalized features. Candidate popularity counts are date-filtered and capped at the train cutoff. Product/category vocabulary construction and eligible catalogue selection use the train-cutoff catalogue; Stage 1 optimization uses that fixed catalogue, while rolling sale/block eligibility is applied in downstream discovery/slate generation.

A correct rolling solution can aggregate demand by unique prediction date, preserve strict `< date`, and group batches by date. Naively recomputing from every event per transition is expensive. Incremental daily prefix/window aggregates reduce preprocessing toward `O(events + dates × products)`, with window expiry and per-category totals; exact median quantities need an incremental quantile structure or sorted groups. Storing `D × P × 6` float32 values costs `24DP` bytes (e.g. 636 dates × 1,722 products ≈ 25.1 MiB; with 636 illustrative dates, the locally stored 790-SKU training catalogue needs about 11.5 MiB and the 13,729-SKU expanded catalogue about 199.8 MiB; unique date counts were not measured from raw purchases). Differentiable ProductTower outputs must be recomputed as weights change; cached **inputs** are safe, cached training **outputs** become stale. All dates, product IDs, scalers, checkpoint provenance and cache versions need explicit binding. This is a behavioral retraining experiment, so it is deliberately deferred.

## Evaluation and artifact integrity

Targets label slates only after candidate selection; existing anti-injection tests confirm target changes do not alter candidates. Rolling candidate indices are mapped back to full catalogue order. History IDs remain **one-based training-vocabulary IDs** (zero unknown/padding); expanded candidates are **zero-based catalogue indices**. Newly admitted SKUs absent from the training history vocabulary remain unknown in memory. Future shared-vector layouts must map by SKU explicitly.

`evaluate_ranker` divides discovery hits by **all** new targets, including missing-slate positives (existing regression). Overall recall and NDCG use complete baskets and macro-average across transitions, whereas new-target recall micro-averages target instances. The full evaluator appends non-slate Stage 1 candidates after the 50 reranked products, so Top-100 and MRR can differ from slate-only training metrics; Top-10 remains aligned for full 50-item slates. Loss and attention summaries currently average batch means without weighting the final short batch; this is a reporting limitation, not a change to per-basket ranking metrics.

Discovery and NDCG selections are independently serialized and use strict improvements; the run-selected alias follows the requested selection. No alias was changed. The current full-evaluation report records epoch 4, while the current `best_ranker.pt` is epoch 7. Thus that report cannot certify the current alias. Saved report numbers and checkpoint metadata are historical evidence only, not newly measured validation results.
